* Introduction
  This document enumerates the features of Plottr Web and details
  outstanding work where features are incomplete.  It also serves as a
  near-exhaustive list of Plottr's features.

* Functional Requirements
  The website is, for the most part, a functioning version of the
  desktop app that's served from a web server.  The following is an
  exhaustive list of the feature set of Plottr, indicating which of
  the features are available on the desktop and web versions of the
  application at the time of writing this document.

** Permissions and Authorisation
    - users start with "owner" permission and can grant "collaborator"
      and "viewer" permission to others.  (Granting permission is a
      work in progress).

    Three permission states exist in the application and are stored as
    "authorisation" documents in Firestore at the path:
    ~/authorisation/{userId}/{ducomentId}/~ and have the schema: ~{
    "permission": "(owner)|(collaborator)|(viewer)" }~.:
     - "owner",
     - "collaborator", and
     - "viewer".

    Permissions are enforced by a set of Firebase rules that are
    checked into the repository.

    Only owners can change "file" records in Firestore.  This data
    includes the file name and metadata.

    Planned but not yet implemented: Only "owners" can add
    collaboration records for other users.

    Collaborators and owners can change any of the other data.  This
    includes values at the keys:
     - ~beats/~
     - ~books/~
     - ~cards/~
     - ~categories/~
     - ~characters/~
     - ~customAttributes/~
     - ~featureFlags/~
     - ~hierarchyLevels/~
     - ~images/~
     - ~lines/~
     - ~notes/~
     - ~places/~
     - ~series/~
     - ~tags/~
     - ~tour/~
     - ~ui/~

    The new "Share" dialog enables a user to view the current
    permissions for the loaded file (see screenshot):

    #+CAPTION: File share dialog.  The current user's permission record is the only entry.

** Collaboration
    - users see each others edits to the same file as they're made.

    Changes to the Redux store are mirrored to Firestore by comparing
    the latest version of the store with the most recent version in
    the undo-history.  The comparison proceeds by deep comparison of
    each root-level key of the Redux store.

    Some actions do not cause a synchronisation call to Firestore.
    This is usually because the details communicated would not be
    relevant to other users or pertain to parts of the store that are
    never stored in Firestore.  The following criteria are used to
    decide whether an action should prompt a corresponding change in
    Firestore:
    1. the action must not be of type ~PERMISSION_ERROR~, ~CLEAR_ERROR~ or
       ~FILE_LOADED~.
    2. The root level key is one of: ~error~, ~permission~, ~ui~, or
       ~project~.
    3. A special attribute called ~patching~ is present on the action
       (useful when an action knows that it shouldn't affect
       Firestore).

    Firestore doesn't support arrays as the root type of a document.
    All arrays are transformed into objects and from objects back into
    arrays when dispatched to and received from Firestore by the
    synchronisation logic.

    When data is synchronised to Firestore, Plottr adds a ~clientId~ to
    the document.  It indicates which session modified the document
    last, where each tab in a browser and each separate browser is
    considered a separate session.  This value enables Plottr to
    differentiate between edits that the were made by other clients
    and the current client.  It's important to be able to
    differentiate between the two because every edit made to Firestore
    is echoed back by snapshot listeners in the Firebase SDK.

* Summary of Remaining Features from Desktop
** Create Character from Template
   Turned off.  Problem is where to store the template.  We can start
   a collection in Firestore quite easily.
** Create Project from Template
   Turned off.  Templates from Github not wired up (requires server
   call).
** Create Template from Timeline
   Turned off.  Problem is where to store the template.  We can start
   a collection in Firestore quite easily.
** Create Template from Character
   Turned off.  Problem is where to store the template.  We can start
   a collection in Firestore quite easily.
** Save list of custom attributes as template
   Turned off.  Problem is where to store the template.  We can start
   a collection in Firestore quite easily.
** File Export
   Not yet implemented or available on UI.  Word export should be
   doable in-browser.  Scrivener requires a server call.
** Account Management
   To be decided: no integration with existing licence server and no
   logic to prevent users from using the website without a license.
** Backup
   To be decided: no decision taken on undo/history and backup.
** Dashboard Features
   No dashboard exists.
*** Account Management
    No dashboard exists.
**** Apply License Key
     No dashboard exists.
**** Apply for More Days
     No dashboard exists.
*** Settings
**** Change Appearance
     Dark versus light mode exists in the app, but there's no way of
     toggling between the two.
**** Change Language
     Language management exists throughout the app, but it doesn't
     hook into existing browser standards nor is there a control on a
     dashboard for convenience.
**** Turn Off/On Act Structure
     No dashboard exists yet.
*** Help
    No dashboard exists yet.
** Error Reporting
   Function currently stubbed out.
** Logging
   Need to use a service such as log rocket, or build our own.
** Export Configuration Management
   We could use browser local storage.
** MPQ
   It's currently a stub.

* Summary of Remaining Web-Only Features
** Share File with Other User
   UI is incomplete for sharing a document with another user.
** Simultaneously Edit RCEs Robustly
   i.e. without clobbering each other's data.
** Download File
   Lacks a UI to trigger download.
** Upload File
   No UI or wiring in the app exists to handle loading a file, but
   this feature would be very simple.
** File Versioning
   Functionally to upgrade files exists.  There is no file version at
   the moment.  It should match desktop to ensure robust upgrades
   between versions.
